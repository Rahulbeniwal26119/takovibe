Celery is a distributed task queue that allows us to offload time-consuming and computing-intensive tasks to background workers, preventing the main thread from blocking.

Celery can be integrated with popular message brokers like RabbitMQ and Redis.

## Step 2: Create Celery Application

Create `celery.py` inside your `django_revision` directory - this serves as the entry point:

```python
# django_revision/celery.py

import os
from celery import Celery
from django.conf import settings

# Set default Django settings module
os.environ.setdefault("DJANGO_SETTINGS_MODULE", "django_revision.settings")

# Create Celery application instance
app = Celery("django_revision")

# Load configuration from celeryconfig.py
app.config_from_object('celeryconfig', namespace='CELERY')

# Auto-discover tasks from installed Django apps
app.autodiscover_tasks(lambda: settings.INSTALLED_APPS)
```

## Step 3: Running Asynchronous Tasks

### Starting the Celery Worker

Start Celery worker to process tasks:

```bash
celery -A django_revision worker -l info
```

### Creating Your First Task

Create `tasks.py` in your `django_revision` directory:

```python
# django_revision/tasks.py

from django_revision.celery import app

@app.task
def send_mail(to_user, from_user, subject, message):
    # Simulate time-consuming email operation
    import time
    time.sleep(10)
    print(f"Mail sent to {to_user} from {from_user}")
    print(f"Subject: {subject}")
    print(f"Message: {message}")
    return "Email sent successfully"

def send_report_synchronously():
    """This will block the main thread"""
    to_user = "user@example.com"
    result = send_mail(to_user, "system@example.com", "Report", "Your report is ready")
    return f"Email sent to {to_user}"
```

Running the synchronous version will block your main thread for 10 seconds:

```
Mail sent to user@example.com from system@example.com
Subject: Report
Message: Your report is ready
'Email sent to user@example.com'
```

This blocking behavior can severely impact your application's performance.

### Using delay() Method

The simplest way to run tasks asynchronously:

```python
# Send task to Celery queue
send_mail.delay("user@example.com", "system@example.com", "Report", "Your report is ready")
```

### Using apply_async() Method

For more advanced control over task execution:

```python
from django_revision.tasks import send_mail

def send_report_asynchronously():
    to_user = "user@example.com"
    
    # Send task with advanced options
    result = send_mail.apply_async(
        args=[to_user, "system@example.com", "Report", "Your report is ready"],
        kwargs={},
        countdown=1,          # Delay execution by 1 second
        retry=True,           # Enable retry on failure
        priority=0,           # Task priority (lower = higher priority)
        queue="default",      # Queue name
        retry_policy={
            "max_retries": 3,
            "interval_start": 0,
            "interval_step": 0.2,
            "interval_max": 0.2,
        }
    )
    return f"Email task queued for {to_user}"
```

### apply_async() Options Explained

- **args**: Positional arguments for the task
- **kwargs**: Keyword arguments for the task  
- **countdown**: Seconds to wait before executing the task
- **retry**: Whether to retry the task on failure
- **retry_policy**: Retry configuration (max retries, intervals)
- **priority**: Task priority (lower number = higher priority)
- **eta**: Specific datetime for task execution
- **expires**: Expiration time for the task
- **queue**: Target queue name

## Step 5: Advanced Task Configuration

You can configure tasks with advanced options using decorators:

```python
from django_revision.celery import app

@app.task(
    name="django_revision.tasks.send_mail_advanced",
    bind=True,                    # Bind task instance as first argument
    autoretry_for=(Exception,),   # Auto-retry on these exceptions
    max_retries=3,                # Maximum retry attempts
    ignore_result=False,          # Store task results
    retry_backoff=3,              # Exponential backoff multiplier
    retry_jitter=0.1,             # Add randomness to retry intervals
    retry_backoff_max=300         # Maximum retry delay (5 minutes)
)
def send_mail_advanced(self, to_user, from_user, subject, message):
    import time
    time.sleep(10)
    print(f"Advanced mail sent to {to_user} from {from_user}")
    return "Advanced email sent successfully"
```

### Task Configuration Options

- **bind**: Provides access to task instance (self)
- **name**: Custom task name (defaults to function name)
- **autoretry_for**: Automatically retry on specified exceptions
- **max_retries**: Maximum number of retry attempts
- **ignore_result**: Whether to store task results
- **retry_backoff**: Exponential backoff multiplier for retries
- **retry_jitter**: Random delay added to retry intervals
- **retry_backoff_max**: Maximum retry delay

### Creating Periodic Tasks

Add periodic tasks to your `tasks.py`:

```python
# django_revision/tasks.py

from celery import shared_task

@shared_task
def greet_user():
    print("Hello User - This is a periodic task!")
    return "Greeting sent"
```

### Configuring Task Schedule

Create `periodic_tasks.py` for schedule configuration:

```python
# django_revision/periodic_tasks.py

from celery.schedules import crontab

CELERY_BEAT_SCHEDULE = {
    'greet-users-every-minute': {
        'task': 'django_revision.tasks.greet_user',
        'schedule': crontab(minute='*/1'),  # Run every minute
    },
    'daily-report': {
        'task': 'django_revision.tasks.generate_daily_report',
        'schedule': crontab(hour=0, minute=0),  # Run daily at midnight
    },
}
```

## Important Concepts

### Key Terms

- **shared_task**: Decorator for creating reusable tasks across multiple Celery apps
- **CELERY_BEAT_SCHEDULE**: Configuration for recurring tasks managed by beat scheduler
- **Crontab**: Unix-style scheduling format (*/1 means "every 1 unit")
- **Worker**: Process that executes tasks from the queue
- **Beat**: Scheduler that sends periodic tasks to the queue
- **Broker**: Message queue system (RabbitMQ, Redis)
- **Backend**: Result storage system (MongoDB, Redis, Database)

### Production Tips

1. **Monitor your queues** - Use tools like Flower for monitoring
2. **Configure proper logging** - Essential for debugging in production
3. **Use connection pooling** - For better database performance
4. **Set appropriate timeouts** - Prevent hanging tasks
5. **Handle failures gracefully** - Implement proper error handling

## 📋 Frequently Asked Questions

<div className="bg-gray-50 dark:bg-gray-800 p-4 rounded-lg">
<h4 className="font-semibold mb-2 text-sm md:text-base">What's the difference between Celery and Django's built-in async support?</h4>
<p className="text-sm md:text-base text-gray-600 dark:text-gray-400">Celery runs tasks in separate processes/machines and persists them in queues, while Django's async is for I/O-bound operations within the same process. Celery is better for heavy computation and distributed systems.</p>
</div>

<div className="bg-gray-50 dark:bg-gray-800 p-4 rounded-lg">
<h4 className="font-semibold mb-2 text-sm md:text-base">Can I use Redis instead of RabbitMQ as the message broker?</h4>
<p className="text-sm md:text-base text-gray-600 dark:text-gray-400">Absolutely! Redis is simpler to set up. Just change the broker_url to `redis://localhost:6379/0`. RabbitMQ is more feature-rich for complex scenarios, but Redis works great for most use cases.</p>
</div>

<div className="bg-gray-50 dark:bg-gray-800 p-4 rounded-lg">
<h4 className="font-semibold mb-2 text-sm md:text-base">How do I handle task failures and retries?</h4>
<p className="text-sm md:text-base text-gray-600 dark:text-gray-400">Use the `autoretry_for`, `max_retries`, and `retry_backoff` parameters in the @task decorator. You can also manually retry with `self.retry()` within the task function.</p>
</div>

<div className="bg-gray-50 dark:bg-gray-800 p-4 rounded-lg">
<h4 className="font-semibold mb-2 text-sm md:text-base">Should I use shared_task or app.task decorator?</h4>
<p className="text-sm md:text-base text-gray-600 dark:text-gray-400">Use `@shared_task` for reusable tasks that don't depend on specific Celery app instances. Use `@app.task` when you need access to the specific Celery app configuration.</p>
</div>

<div className="bg-gray-50 dark:bg-gray-800 p-4 rounded-lg">
<h4 className="font-semibold mb-2 text-sm md:text-base">How many workers should I run in production?</h4>
<p className="text-sm md:text-base text-gray-600 dark:text-gray-400">Start with number of CPU cores × 2, then monitor and adjust based on your task types. CPU-bound tasks need fewer workers, I/O-bound tasks can handle more. Use `--concurrency` flag to set this.</p>
</div>

<div className="bg-gray-50 dark:bg-gray-800 p-4 rounded-lg">
<h4 className="font-semibold mb-2 text-sm md:text-base">What's the best way to monitor Celery in production?</h4>
<p className="text-sm md:text-base text-gray-600 dark:text-gray-400">Use Flower for real-time monitoring, set up proper logging, and consider tools like Prometheus + Grafana for metrics. Monitor queue length, task success/failure rates, and worker health.</p>
