Welcome back, everyone! 🎉  

This article is part of my *Low Level Design* series, where we explore the **SOLID principles** of software design. Today, we’ll discuss the **Open/Closed Principle (OCP)** — the “O” in SOLID.  

👉 Definition:  
> **Software entities should be open for extension but closed for modification.**  

This means once code is tested and working, we should be able to extend its behavior without rewriting or modifying the existing implementation.  

---

## 🔹 Why is OCP Important?

- **Avoid Breaking Existing Code** – No changes in stable code when adding features.  
- **Easier Maintenance** – You only write new code instead of digging into old, tested code.  
- **Scalability** – You can add new behavior without a domino effect of modifications.  
- **Reduced Coupling** – Each class is less dependent on others.  

---

## ❌ Not Following OCP (Bad Example)

Consider an **AreaCalculator** for shapes.  

### Python Example

```python
import math

class Circle:
    def __init__(self, radius):
        self.radius = radius

class Square:
    def __init__(self, side_length):
        self.side_length = side_length

class AreaCalculator:
    def total_area(self, shapes):
        total = 0
        for shape in shapes:
            if shape.__class__ == Circle:
                total += math.pi * shape.radius ** 2
            elif shape.__class__ == Square:
                total += shape.side_length ** 2
            else:
                raise ValueError("Unknown shape type")
        return total

shapes = [Circle(5), Square(4)]
print("Total area:", AreaCalculator().total_area(shapes))
```

### Rust Example

```rust
enum Shape {
    Circle(f64),
    Square(f64),
}

struct AreaCalculator;

impl AreaCalculator {
    fn area(shapes: Vec<Shape>) -> f64 {
        let mut total_area = 0.0;
        for s in shapes {
            match s {
                Shape::Circle(radius) => total_area += std::f64::consts::PI * radius * radius,
                Shape::Square(side) => total_area += side * side,
            }
        }
        total_area
    }
}
```

⚠ Problem: Every time we add a new shape (e.g., `Triangle`), we must **edit AreaCalculator**. This violates OCP.  

---

## ✅ Following OCP (Refactored)

We make `Shape` an interface (abstract class or trait) where each shape defines its own `area()` method.  

### Python Example

```python
import math

class Shape:
    def area(self):
        raise NotImplementedError("Subclasses must implement this method")

class Circle(Shape):
    def __init__(self, radius):
        self.radius = radius
    def area(self):
        return math.pi * self.radius ** 2

class Square(Shape):
    def __init__(self, side_length):
        self.side_length = side_length
    def area(self):
        return self.side_length ** 2

class Triangle(Shape):
    def __init__(self, a, b, c):
        self.a = a
        self.b = b
        self.c = c
    def area(self):
        s = (self.a + self.b + self.c) / 2
        return math.sqrt(s * (s - self.a) * (s - self.b) * (s - self.c))

class AreaCalculator:
    @classmethod
    def total_area(cls, shapes):
        return sum(shape.area() for shape in shapes)

shapes = [Circle(5), Square(4), Triangle(3, 4, 5)]
print("Total area:", AreaCalculator.total_area(shapes))
```

Adding a new shape (e.g., `Rectangle`) requires **no change** to `AreaCalculator`.  

---

### Rust Example

```rust
use std::f64::consts::PI;

trait Shape {
    fn area(&self) -> f64;
}

struct Circle { radius: f64 }
struct Square { side: f64 }
struct Rectangle { width: f64, height: f64 }
struct Triangle { a: f64, b: f64, c: f64 }

impl Shape for Circle {
    fn area(&self) -> f64 { PI * self.radius * self.radius }
}

impl Shape for Square {
    fn area(&self) -> f64 { self.side * self.side }
}

impl Shape for Rectangle {
    fn area(&self) -> f64 { self.width * self.height }
}

impl Shape for Triangle {
    fn area(&self) -> f64 {
        let s = (self.a + self.b + self.c) / 2.0;
        (s * (s - self.a) * (s - self.b) * (s - self.c)).sqrt()
    }
}

struct AreaCalculator;

impl AreaCalculator {
    fn total_area(shapes: &[Box<dyn Shape>]) -> f64 {
        shapes.iter().map(|s| s.area()).sum()
    }
}

fn main() {
    let shapes: Vec<Box<dyn Shape>> = vec![
        Box::new(Circle { radius: 5.0 }),
        Box::new(Square { side: 4.0 }),
        Box::new(Rectangle { width: 2.0, height: 3.0 }),
        Box::new(Triangle { a: 3.0, b: 4.0, c: 5.0 }),
    ];
    println!("Total area: {}", AreaCalculator::total_area(&shapes));
}
```

Now, `AreaCalculator` never changes. Adding shapes only requires extending the `Shape` trait.

## 🔹 Real-World Analogy

A smartphone OS follows OCP:  
- The **core system** stays stable (closed for modification).  
- We can **add new apps** to extend functionality (open for extension).  

---

## 🙋 FAQ

**Q1: How do I know if I’m violating OCP?**  
If you keep editing existing classes to add new cases, you’re not following OCP.  

**Q2: Is OCP only for OOP languages?**  
No. The principle applies across paradigms — plugins, modules, and extension functions also follow OCP.  

**Q3: What’s the main benefit?**  
Stable, bug-free core logic that can grow via extensions.  

---

## 🙏 Conclusion

The **Open/Closed Principle (OCP)** is a powerful way to design scalable, extensible, and stable systems.  

- **Bad Design** → AreaCalculator needs edits for every new shape.  
- **Good Design** → Shapes extend a base interface, and the calculator remains untouched.  

By designing for **extension without modification**, you ensure long-term maintainability and flexibility.
