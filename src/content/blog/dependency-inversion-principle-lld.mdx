## What is the Dependency Inversion Principle?

The Dependency Inversion Principle (DIP) states:

> **High-level modules should not depend on low-level modules. Both should depend on abstractions.**  
> **Abstractions should not depend on details; details should depend on abstractions.**

✅ In simple terms: insert an abstraction layer between **business logic** (high-level) and **implementation details** (low-level).

---

## Why DIP Matters?

- 🔌 **Looser Coupling** → Business logic isn’t tied to one implementation.  
- 🧪 **Improved Testability** → Easy to mock dependencies.  
- 🚀 **Flexibility & Extensibility** → Swap out details (e.g., Email → SMS → Push notifications) without touching the core logic.

## Without DIP ❌

### Python

```python
class SendEmail:
    def send(self, message):
        print(f"Sending email: {message}")

class NotificationService:
    def __init__(self, email_sender):
        # tightly coupled with Email
        self.email_sender = email_sender

    def notify(self, message):
        self.email_sender.send(message)

service = NotificationService(SendEmail())
service.notify("Welcome to SOLID!")
```

⚠️ Problems:  
- Hard to extend (SMS, push, etc.).  
- Violates OCP.  
- Difficult to test without a real email sender.  

### Rust

```rust
struct SendEmail;

impl SendEmail {
    fn send(&self, message: &str) {
        println!("Sending email: {}", message);
    }
}

struct NotificationService {
    email_sender: SendEmail,
}

impl NotificationService {
    fn new(email_sender: SendEmail) -> Self {
        NotificationService { email_sender }
    }

    fn notify(&self, message: &str) {
        self.email_sender.send(message);
    }
}

fn main() {
    let service = NotificationService::new(SendEmail);
    service.notify("Welcome to SOLID series!");
}
```

## With DIP ✅

### Python

```python
from abc import ABC, abstractmethod

class Notifier(ABC):
    @abstractmethod
    def send(self, message): ...

class SendEmail(Notifier):
    def send(self, message):
        print(f"Sending email: {message}")

class SendSMS(Notifier):
    def send(self, message):
        print(f"Sending SMS: {message}")

class NotificationService:
    def __init__(self, notifier: Notifier):
        self.notifier = notifier

    def notify(self, message):
        self.notifier.send(message)

# Plug-and-play implementations
NotificationService(SendEmail()).notify("Hello via Email!")
NotificationService(SendSMS()).notify("Hello via SMS!")
```

### Rust

```rust
trait Notifier {
    fn send(&self, message: &str);
}

struct SendEmail;
struct SendSMS;

impl Notifier for SendEmail {
    fn send(&self, message: &str) {
        println!("Sending Email: {}", message);
    }
}

impl Notifier for SendSMS {
    fn send(&self, message: &str) {
        println!("Sending SMS: {}", message);
    }
}

struct NotificationService<T: Notifier> {
    notifier: T,
}

impl<T: Notifier> NotificationService<T> {
    fn new(notifier: T) -> Self {
        NotificationService { notifier }
    }

    fn notify(&self, message: &str) {
        self.notifier.send(message);
    }
}

fn main() {
    let email_service = NotificationService::new(SendEmail);
    email_service.notify("Hello via Email!");

    let sms_service = NotificationService::new(SendSMS);
    sms_service.notify("Hello via SMS!");
}
```

## DIP and Other SOLID Principles

- **DIP + OCP** → Extend via new implementations, no need to modify core logic.  
- **DIP + ISP** → Interfaces should be small & focused, keeping dependencies clean.  
- **DIP + LSP** → Abstractions must be substitutable for correctness.  
- **DIP + SRP** → Classes stay focused, dependencies inverted for flexibility.

## 📌 SOLID Recap (Cheat Sheet)

Here’s a quick recap of all five principles with links:

1. **SRP – Single Responsibility Principle** → [Read SRP Guide](./single-responsibility-principle-lld)  
   *One class = one reason to change.*  

2. **OCP – Open/Closed Principle** → [Read OCP Guide](./open-closed-principle-lld)  
   *Open for extension, closed for modification.*  

3. **LSP – Liskov Substitution Principle** → [Read LSP Guide](./liskov-substitution-principle-lld)  
   *Subtypes must be substitutable for their base types.*  

4. **ISP – Interface Segregation Principle** → [Read ISP Guide](./interface-segregation-principle-lld)  
   *Many small, specific interfaces > one fat interface.*  

5. **DIP – Dependency Inversion Principle** (this article)  
   *High-level & low-level depend on abstractions.*

## ❓ FAQ

**Q: Is DIP the same as Dependency Injection?**  
A: Not exactly. DIP is the principle; dependency injection is one way to implement it.  

**Q: Do I always need interfaces for DIP?**  
A: Not always — but whenever high-level depends directly on low-level, DIP is likely being violated.
