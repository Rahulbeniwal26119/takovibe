Welcome back, everyone! 🎉  

This article is part of my *Low Level Design* series, where we explore the **SOLID principles** of clean code. Today, we’ll cover the **Single Responsibility Principle (SRP)** — the first principle in SOLID.  

👉 In short:  
> A class, function, or module should have **only one reason to change**.  

---

## 🔹 What is SRP?

The Single Responsibility Principle (SRP) was introduced by **Robert C. Martin (Uncle Bob)**.  

It means:  
- Each class should handle **one responsibility**.  
- A class that does multiple unrelated things becomes hard to test, maintain, and extend.  

---

## 🔹 Why SRP is Important?

- **Isolation of Changes** – Changes to one responsibility won’t break unrelated parts.  
- **Improved Clarity** – Each part of the system has a clear and well-defined purpose.  
- **Better Testability** – Focused components are easier to test.  
- **Maintainability** – Adding new features or fixing bugs becomes easier.  

---

## ❌ Common Mistakes

1. **God Classes** – A single class that does everything.  
2. **Overloaded Functions** – Functions doing multiple unrelated steps.  
3. **Over-separation** – Creating too many tiny classes for trivial responsibilities.  

👉 Rule of thumb: If you can describe a class with “and” (“This class does X and Y”), it likely violates SRP.  

---

## ❌ Example of a God Class (Python)

```python
from dataclasses import dataclass

@dataclass
class BadUser:
    first_name: str
    last_name: str
    email: str

    @classmethod
    def create_user(cls, first_name, last_name, email):
        print(f"saving user to database: {email}")
        user = cls(first_name, last_name, email)
        print(f"sending welcome email to {user.email}")
        return user
    
    def generate_order_report(self):
        print(f'generating order report for {self.email}')
```

⚠ Problems:  
- `BadUser` is doing **user data management**, **persistence**, **email sending**, and **report generation**.  
- One change (like database logic) could break others (email sending).

## ✅ SRP Example in Python

Let’s refactor:  

```python
class User:
    def __init__(self, name: str, email: str):
        self.name = name
        self.email = email

class UserRepository:
    def __init__(self):
        self.users = []

    def add_user(self, user: User):
        self.users.append(user)

    def list_users(self):
        return self.users

class NotificationService:
    def send_welcome_email(self, user: User):
        print(f"Notification: Sending welcome email to {user.email}")

class UserService:
    def __init__(self, repository: UserRepository, notifier: NotificationService):
        self.repository = repository
        self.notifier = notifier

    def register_user(self, name: str, email: str):
        user = User(name, email)
        self.repository.add_user(user)
        self.notifier.send_welcome_email(user)
        return user
```

✔ Each class now has a **single responsibility**.

## ✅ SRP Example in Rust

```rust
struct User {
    name: String,
    email: String,
}

impl User {
    fn new(name: &str, email: &str) -> Self {
        Self {
            name: name.to_string(),
            email: email.to_string(),
        }
    }
}

struct UserRepository {
    users: Vec<User>,
}

impl UserRepository {
    fn new() -> Self {
        Self { users: vec![] }
    }

    fn add_user(&mut self, user: User) {
        self.users.push(user)
    }

    fn list_users(&self) -> &Vec<User> {
        &self.users
    }
}

struct NotificationService;

impl NotificationService {
    fn send_welcome_email(&self, user: &User) {
        println!("Notification: Sending welcome email to {}", user.email)
    }
}

struct UserService {
    repository: UserRepository,
    notifier: NotificationService,
}

impl UserService {
    fn new(repository: UserRepository, notifier: NotificationService) -> Self {
        Self { repository, notifier }
    }

    fn register_user(&mut self, name: &str, email: &str) {
        let user = User::new(name, email);
        self.repository.add_user(user);
        if let Some(last_user) = self.repository.list_users().last() {
            self.notifier.send_welcome_email(last_user);
        }
    }
}
```

✔ Same design principle applied in Rust.

## 🔹 Benefits of SRP

- **Easier Maintenance** – Modify one class without affecting others.  
- **Improved Readability** – Classes are smaller and easier to understand.  
- **Simpler Testing** – Each component can be tested independently.  
- **Reusability** – Components with clear boundaries can be reused elsewhere.  

---

## 🔹 Real-World Applications

- **Web Frameworks (MVC/MVT)** – Models, Views, and Controllers each have distinct roles.  
- **E-commerce Systems** – Order validation, payment, inventory, and notifications are handled separately.  
- **Microservices** – Each service focuses on a single business capability.  

---

## 🙋 FAQ

**Q1: Does SRP mean only one method per class?**  
No. A class can have multiple methods as long as they relate to the same responsibility.  

**Q2: Can SRP apply outside OOP?**  
Yes! Functions, modules, and even services in microservice architecture can follow SRP.  

**Q3: How do I know if a class violates SRP?**  
If changing one functionality forces unrelated changes, it’s violating SRP.  

**Q4: Does function length matter in SRP?**  
No. A function can be long but still follow SRP if it does one logical thing.

## 🙏 Conclusion

The **Single Responsibility Principle (SRP)** ensures your code is:  
- Clean 🧹  
- Modular 🧩  
- Testable ✅  
- Maintainable 🔧  

Whether in Python, Rust, or any other language, SRP helps you design software that is easier to evolve and less prone to bugs.
