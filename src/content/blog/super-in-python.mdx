> **TL;DR** `super()` is the *safest* way to call parent classes in Python. It respects the *Method Resolution Order* (MRO) so each base class is initialised **once**—even in complex diamond-inheritance hierarchies.

Python fully embraces object-oriented programming (OOP), but multiple inheritance can quickly become a minefield. If you’ve ever copy-pasted `BaseClass.__init__(self)` calls or wrestled with unpredictable initialisation order, this post is for you.

Below we’ll diagnose the most common pitfalls *without* `super()`, then solve them cleanly *with* it—no magic, just MRO.

---

## 1. Useless `BaseClass` position during initialisation

Without `super()`, manually calling a parent’s `__init__` locks you into a fragile, hard-coded order.

```python
class BaseClassA:
    def __init__(self, value1):
        self.value1 = value1

class BaseClassB:
    def __init__(self, value2):
        self.value2 = value2

class TimeSeven(BaseClassA):
    def __init__(self, value1):
        BaseClassA.__init__(self, value1)
        self.value1 *= 7

class PlusFive(BaseClassB):
    def __init__(self, value2):
        BaseClassB.__init__(self, value2)
        self.value2 += 5

class OneWay(PlusFive, TimeSeven):
    def __init__(self, value1, value2):
        TimeSeven.__init__(self, value1)
        PlusFive.__init__(self, value2)
        print(self.value1, self.value2)

OneWay(100, 200)
# Output: 700 205
```

Changing the base-class order **doesn’t** change the initialisation order (because you hard-coded it):

```python
class OneWay(TimeSeven, PlusFive):
    def __init__(self, value1, value2):
        TimeSeven.__init__(self, value1)
        PlusFive.__init__(self, value2)
        print(self.value1, self.value2)

OneWay(100, 200)
# Output: 700 205
```

## 2. The diamond-inheritance nightmare

![Python diamond inheritance diagram](https://miro.medium.com/v2/resize:fit:1100/format:webp/1*tGQ4lEJLSyINQe3siWAsgQ.png "Diagram of the diamond problem in Python multiple inheritance")

```python
class BaseClass:
    def __init__(self, value):
        self.value = value

class TimeSeven(BaseClass):
    def __init__(self, value):
        BaseClass.__init__(self, value)
        self.value *= 7

class PlusFive(BaseClass):
    def __init__(self, value):
        BaseClass.__init__(self, value)
        self.value += 5

class OneWay(TimeSeven, PlusFive):
    def __init__(self, value):
        TimeSeven.__init__(self, value)
        PlusFive.__init__(self, value)

obj = OneWay(100)
print(obj.value)
# Output: 105
```

Switching the order flips the behaviour:

```python
class OneWay(TimeSeven, PlusFive):
    def __init__(self, value):
        PlusFive.__init__(self, value)
        TimeSeven.__init__(self, value)

obj = OneWay(100)
print(obj.value)
# Output: 700
```

Two bugs for the price of one! Let’s fix this mess.

## 3. Enter `super()` + MRO (C3 linearisation)

```python
class BaseClass:
    def __init__(self, value):
        self.value = value

class TimeSeven(BaseClass):
    def __init__(self, value):
        super().__init__(value)
        self.value *= 7

class PlusFive(BaseClass):
    def __init__(self, value):
        super().__init__(value)
        self.value += 5

class OneWay(TimeSeven, PlusFive):
    def __init__(self, value):
        super().__init__(value)

print(OneWay(100).value)
print("MRO -> ", OneWay.mro())
# Output: 735
# MRO -> [<class '__main__.OneWay'>, <class '__main__.TimeSeven'>, <class '__main__.PlusFive'>, <class '__main__.BaseClass'>, <class 'object'>]
```

Change the base-class order and the result updates safely:

```python
class OneWay(PlusFive, TimeSeven):
    def __init__(self, value):
        super().__init__(value)

print(OneWay(100).value)
print("MRO -> ", OneWay.mro())
# Output: 705
# MRO -> [<class '__main__.OneWay'>, <class '__main__.PlusFive'>, <class '__main__.TimeSeven'>, <class '__main__.BaseClass'>, <class 'object'>]
```

### Using `super()` with arguments

```python
class OneWay(PlusFive, TimeSeven):
    def __init__(self, value):
        super(PlusFive, self).__init__(value)

print(OneWay(100).value)
# Output: 700

class OneWay(PlusFive, TimeSeven):
    def __init__(self, value):
        super(TimeSeven, self).__init__(value)

print(OneWay(100).value)
# Output: 100
```

Changing the *starting* superclass changes where MRO kicks off, hence different totals.

## Key takeaways

- **Always** prefer `super()` in hierarchy-aware classes; it’s future-proof and DRY.
- Python’s **C3 linearisation** guarantees every parent runs only once in a predictable order.
- Avoid manually hard-coding `Parent.__init__` calls unless you *really* need fine-grained control (and you most likely don’t).

## Frequently Asked Questions (FAQs)

### 1. What does `super()` actually return?

`super()` returns a *proxy object* that routes method calls to the next class in the MRO, starting just after the current class. That’s why you can call `super().__init__()` without naming the parent explicitly.

### 2. Can I use `super()` outside `__init__`?

Absolutely. Any instance method—`__str__`, `save`, `close`, etc.—can delegate work upstream with `super().method()`.

### 3. When should I avoid `super()`?

If your class hierarchy is *single* inheritance (only one direct parent) and you’re positive it will never change, manually calling the parent may be fine. Otherwise, default to `super()`.

### 4. How do keyword arguments flow through `super()`?

Design your `__init__` signatures to accept `*args` and `**kwargs`, then pass them along via `super().__init__(*args, **kwargs)`. Each class pops what it needs, leaving the rest for upstream classes.

### 5. Why does `super()` sometimes raise `TypeError: super(type, obj): obj must be an instance or subtype of type`?

This happens when you call `super(Class, instance)` but `instance` isn’t actually an instance (or subclass) of `Class`. Double-check you’re passing the right object.

### 6. Is `super()` slower than direct parent calls?

Negligibly. The clarity and safety you gain far outweigh the microseconds lost. Premature optimisation is the real performance killer here.
