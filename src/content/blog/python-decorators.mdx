## 🎯 Why Another Decorator Article?


> *Because decorators feel like “magic” until they don’t.*  
> This guide distills years of real‑world Python experience—Django backends, Flask micro‑services, and hobby scripts—into a pragmatic, copy‑paste‑ready reference.

Decorators in **Python** are a *design pattern* that let you wrap a callable (function, method, or class) with extra behavior **without** editing its original source code. Thanks to Python’s *first‑class functions*, this pattern feels almost built‑in.

---

## 1. The Problem Decorators Solve

- **Cross‑cutting concerns**—logging, caching, authentication—scatter identical boilerplate across multiple functions.  
- **Maintainability** suffers when you decide to tweak the boilerplate everywhere.  
- With a decorator, you extract this extra behavior into a *single* reusable wrapper.

---

## 2. From Closures to Decorators

### 2.1 Write a Closure

```python
def decorate(fn):
    def wrapper(*args, **kwargs):
        print("Executing", fn.__name__)
        return fn(*args, **kwargs)
    return wrapper
```

```python
def add(a, b): return a + b

add = decorate(add)  # 👈 manual wrapping
```

### 2.2 Upgrade to the `@` Syntax

```python
@decorate
def add(a, b): return a + b
```

Both snippets yield identical behavior—but the second is *way* easier to scan.

---

## 3. What’s Really Happening? (3 Callables)

1. Your original `add`  
2. The higher‑order function `decorate`  
3. The returned `wrapper` that Python binds to the symbol `add`

## 4. Class‑Based Decorators

Any class implementing `__call__` qualifies as a decorator:

```python
class decorate:
    def __init__(self, fn):
        self.fn = fn

    def __call__(self, *args, **kwargs):
        print("Executing", self.fn.__name__)
        return self.fn(*args, **kwargs)

@decorate
def get_square(n): return n ** 2
```

Provides a neat way to maintain **state** across calls (e.g., counting invocations).

## 5. Practical Examples

### 5.1 Log Execution Time

```python
import time, functools

def log_time(func):
    @functools.wraps(func)  # keep metadata intact
    def wrapper(*args, **kwargs):
        start = time.perf_counter()
        result = func(*args, **kwargs)
        print(f"{func.__name__} took {time.perf_counter() - start:.4f}s")
        return result
    return wrapper
```

### 5.2 In‑Memory Cache (Memoization)

```python
def add_cache(func):
    cache = {}
    @functools.wraps(func)
    def wrapper(*args):
        if args in cache:
            return cache[args]
        cache[args] = func(*args)
        return cache[args]
    return wrapper
```

Apply them together:

```python
@log_time
@add_cache
def calculate_pow(a, b): return a ** b
```

### 5.3 Rate‑Limit Calls (Decorator With Args)

```python
def limit_invoke_with_time(seconds: int = 5):
    def decorator(func):
        last_call = 0
        @functools.wraps(func)
        def wrapper(*args, **kwargs):
            nonlocal last_call
            now = time.time()
            if now - last_call < seconds:
                raise RuntimeError("Too many calls — slow down!")
            last_call = now
            return func(*args, **kwargs)
        return wrapper
    return decorator
```

Usage styles:

```python
@limit_invoke_with_time          # default 5 s
def foo(): ...

@limit_invoke_with_time()        # same as above
def bar(): ...

@limit_invoke_with_time(10)      # custom interval
def baz(): ...
```

## 6. Built‑In & Third‑Party Decorators You Already Know

| Decorator | Module/Framework | Role |
|-----------|------------------|------|
| `@staticmethod`, `@classmethod`, `@property` | `builtins` | OOP helpers |
| `@dataclass` | `dataclasses` | Boilerplate‑free data objects |
| `@lru_cache` | `functools` | Memoization with size limit |
| `@login_required` | Django | Route‑level auth |
| `@app.route` | Flask | URL routing |

---

## 7. Best Practices

1. **Always use `functools.wraps`** to preserve function metadata.  
2. Accept *all* positional and keyword arguments: `*args, **kwargs`.  
3. Decorators add at least one stack frame—profile performance hotspots.  
4. Prefer **idempotent** decorators so they can stack safely.  
5. Document side effects and global state explicitly.

---

## 8. Performance Notes

For most apps the overhead is negligible. But if you’re wrapping a tight loop or a numerical kernel, consider:

- Swapping Python loops for NumPy / Cython  
- Using `@lru_cache(maxsize=...)` instead of a hand‑rolled dict  
- Benchmarking with `timeit` before and after

## 9. FAQs

<details>
<summary>What exactly is a decorator in Python?</summary>
It’s a callable (function or class) that takes another callable and returns a new callable with extra behavior—typically used for logging, caching, authentication, and more.
</details>

<details>
<summary>How do I write a decorator that accepts parameters?</summary>
Wrap your decorator in a *decorator factory*: an outer function that takes the parameters and returns the actual decorator.
</details>

<details>
<summary>Can decorators be chained together?</summary>
Yes. Python applies them *bottom‑up*: the decorator closest to the function runs first.
</details>

<details>
<summary>Do decorators hurt performance?</summary>
Usually not, but stacking many on a hot path can add measurable latency—always profile critical code.
</details>

<details>
<summary>Where are decorators used in Django and Flask?</summary>
Django uses decorators like `@login_required` for auth; Flask uses `@app.route` and similar for URL routing, middleware, and CORS.
</details>

<details>
<summary>What’s the difference between `@staticmethod` and `@classmethod`?</summary>
`@staticmethod` gets *no* implicit first argument; `@classmethod` receives the class (`cls`) as its first argument, allowing factory methods.
</details>
