Greetings, everyone! 🎉  

This is the **third article** in my *SOLID principles* series. Today, we’re covering the **Liskov Substitution Principle (LSP)** — the “L” in SOLID.  

👉 Definition (Barbara Liskov, 1987):  
> *If S is a subtype of T, then objects of type T may be replaced with objects of type S without altering the correctness of the program.*  

In simpler words:  
If you use a **subclass** anywhere the **parent class** is expected, everything should work correctly — without special handling or broken assumptions.  

---

## 🔹 Key Rules of LSP

1. **No Strengthened Preconditions**  
   A subclass should not demand stricter input than the parent.  
   (e.g., Base accepts all positive numbers → subclass must not restrict to even numbers only).  

2. **No Weakened Postconditions**  
   A subclass should not weaken the output guarantees.  
   (e.g., Base guarantees non-empty strings → subclass must not return empty strings).  

If a subclass cannot meet the promises of its base, it **shouldn’t be a subclass at all**.  

---

## ❌ Violating LSP (Rectangle vs Square Problem)

This is the classic example.  

```python
from dataclasses import dataclass

@dataclass
class Rectangle:
    width: int
    height: int

    def set_height(self, height: int):
        self.height = height
    
    def set_width(self, width: int):
        self.width = width

    def area(self):
        return self.width * self.height

class Square(Rectangle):
    def set_width(self, width):
        self.width = width
        self.height = width
    
    def set_height(self, height):
        self.height = height
        self.width = height

def process_rectangle(rectangle: Rectangle):
    rectangle.set_height(20)
    rectangle.set_width(10)
    assert rectangle.area() == 200, f"Expected 200, got {rectangle.area()}"

rect = Rectangle(5, 10)
sq = Square(5, 5)

process_rectangle(rect)  # Works fine
process_rectangle(sq)    # ❌ AssertionError
```

⚠ The `Square` changes the behavior of `set_width`/`set_height`, breaking the expectations of `Rectangle`.  

---

## ✅ Fixing LSP with Better Abstraction

Instead of forcing `Square` to be a `Rectangle`, both should inherit from a more general `Shape`.  

```python
from abc import ABC, abstractmethod
from dataclasses import dataclass

class Shape(ABC):
    @abstractmethod
    def area(self):
        pass

@dataclass
class Rectangle(Shape):
    width: int
    height: int
    def area(self):
        return self.width * self.height

@dataclass
class Square(Shape):
    side: int
    def area(self):
        return self.side * self.side

def print_area(shape: Shape):
    print(f"Area: {shape.area()}")

print_area(Rectangle(5, 10))  # 50
print_area(Square(5))         # 25
```

✔ Now both follow LSP. No broken assumptions.

## ❌ LSP Violation in Rust

```rust
trait Shape {
    fn set_height(&mut self, h: f64);
    fn set_width(&mut self, w: f64);
    fn area(&self) -> f64;
}

struct Rectangle { height: f64, width: f64 }

impl Shape for Rectangle {
    fn set_height(&mut self, h: f64) { self.height = h; }
    fn set_width(&mut self, w: f64) { self.width = w; }
    fn area(&self) -> f64 { self.height * self.width }
}

struct Square { side: f64 }

impl Shape for Square {
    fn set_height(&mut self, h: f64) { self.side = h; }
    fn set_width(&mut self, w: f64) { self.side = w; }
    fn area(&self) -> f64 { self.side * self.side }
}

fn process_shape(shape: &mut impl Shape) {
    shape.set_height(10.0);
    shape.set_width(5.0);
    assert!(shape.area() == 50.0, "Expected 50.0");
}
```

⚠ Passing a `Square` will fail the assumption.  

---

## ✅ LSP in Rust (Correct Approach)

Use traits with only shared guarantees.  

```rust
trait Shape {
    fn area(&self) -> f64;
}

struct Rectangle { height: f64, width: f64 }
struct Square { side: f64 }

impl Shape for Rectangle {
    fn area(&self) -> f64 { self.height * self.width }
}
impl Shape for Square {
    fn area(&self) -> f64 { self.side * self.side }
}

fn process_shape(shape: &impl Shape) {
    println!("Area: {}", shape.area());
}

fn main() {
    let rect = Rectangle { width: 5.0, height: 10.0 };
    let sq = Square { side: 5.0 };
    process_shape(&rect);
    process_shape(&sq);
}
```

✔ Both types now satisfy `Shape` without breaking expectations.

## 🔹 Why LSP Matters

- Ensures **true polymorphism** — subclasses can replace parents seamlessly.  
- Builds on **OCP** — you can extend systems safely.  
- Makes **testing easier** — mocks/subclasses can be used reliably.  
- Reduces **special-case code** — no more `if isinstance(obj, Square)` checks.  

---

## 🙋 FAQ

**Q1: How do I detect LSP violations?**  
If you’re writing `if subclass then... else...` checks, or subclasses throw exceptions for parent methods, you’re breaking LSP.  

**Q2: Is LSP only for OOP languages?**  
No. Even in Rust, Go, or functional languages, the idea of honoring contracts across abstractions still applies.  

**Q3: Should Square inherit from Rectangle?**  
Not in code! Even though “Square is a Rectangle” mathematically, in programming their contracts differ. Better: both extend `Shape`.  

---

## 🙏 Conclusion

The **Liskov Substitution Principle** ensures that your abstractions remain consistent and reliable.  

- Subtypes must honor the contracts of their base types.  
- Violations lead to leaky abstractions and broken polymorphism.  
- Correct designs use the right abstraction hierarchy (e.g., `Shape` → `Rectangle` & `Square`).  

Follow LSP, and you’ll write **extensible, testable, and bug-free** software.
